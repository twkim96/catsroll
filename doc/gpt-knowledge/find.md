# 원하는 캐릭터까지의 경로 찾기

계산은 사용자 기기에서 실행한다. `prepared`는 계산 전이다. 획득·경로는 앱 결과나 사용자가 제공한 계산표·스크린샷·경로 텍스트에서 확인되는 범위로 설명하며, 자료에 없는 경로가 필요할 때만 새 계산·공유를 요청한다.
확뽑·특수 티켓 예산을 임의로 늘리지 않고, 목표별 티켓 허용과 사용 한도를 구분한다.

## 짧은 답

Find는 선택한 배너들을 어떤 순서로 뽑으면 목표를 얻는지, 정한 범위와 자원 한도 안에서 탐색한다.
표에 목표가 보인다는 사실만으로 현재 위치에서 갈 수 있다고 판단하지 않는다. 경로는 중복 레어·확정·티켓 사용을 함께 계산해야 한다.

## 초심자에게 물을 것

1. 현재 시드와 게임 지역. 모르면 `seed`부터 안내한다.
2. 원하는 캐릭터 이름. `catsroll_cats`로 ID를 찾고 별명이 애매하면 확인한다.
3. 사용할 배너와 “확뽑·플티·레전드 티켓을 써도 되나요? 각각 최대 몇 번인가요?”

세 항목을 한꺼번에 묻지 않는다. 처음에는 시드 유무와 목표만 확인하고,
다음 차례에 필요한 배너·허용 자원을 좁힌다.
이미 말한 정보는 다시 묻지 않는다. 사용자가 모르는 기술 옵션을 한꺼번에 늘어놓지 않는다.
허용받지 않은 티켓/확뽑은 한도를 0으로 유지한다. 각 목표의 `allow_ticket`과 티켓 총 한도는 별도 설정이다.
올컬 자동 선택에서도 `targetSelection.allowTicket`은 기본 false다. 사용자가 목표를 특수티켓으로
얻어도 된다고 명시한 경우에만 true로 설정하고 `maxPlatinum`/`maxLegendTicket`은 별도 한도로 유지한다.

## 준비와 설명

`catsroll_prepare(mode="multi", findEnabled=true)`에 목표·배너·허용 자원을 넣고 앱에서 계산하게 한다.
배열과 Find는 같은 화면이다. 목표는 실제 캐릭터 선택 목록에서 고르며 `cat_id`와 `cat_name`을 함께 넘긴다.
`mode="find"`도 이전 연결과의 호환을 위해 같은 Multi 화면으로 연다.
배열 계산 뒤 Found cats 목록에서 캐릭터별 좌표를 확인할 수 있다.
Find 성공 경로는 표에 도장을 찍으며, 플랜 모드에서 그리기·직접 선택·저장할 수 있다.
GPT 앱의 플랜 저장은 해당 앱 세션 동안 유지된다.
현재 Find는 한 지역의 배너끼리 사용한다. MCP의 기본 탐색 범위는 100행이며 필요한 경우 최대 300행까지 늘릴 수 있다. 이 범위는 뽑기 수가 아니다. 경로에서 실제 사용한 총 뽑기 수는 계산 결과의 `totalDraws`로 확인한다.
서로 다른 날짜의 배너를 실제로 사용할 계획이면 `scheduleAware=true`로 일정 순서도 확인한다.
기본값 false로 얻은 결과를 “오늘 전부 실행 가능”이라고 말하지 않는다.

## 달력: 배너 일정 순서 고려

달력은 **배너 일정 순서 고려** 스위치다. OFF(기본)는 선택한 풀을 일정 제약 없이 비교한다.
ON은 배너의 시작일 포함·종료일 제외 구간을 적용해 날짜 진행을 되돌리지 않는다.
미래 배너로 넘어간 뒤 종료된 과거 배너를 다시 쓰는 경로를 제외하며, 기간이 겹치는 두 배너는
겹치는 구간에 함께 쓸 수 있다. 종료일과 다음 시작일이 같으면 겹치지 않는다.
현재 엔진은 배너의 **날짜 구간**을 비교한다. 현재 시각·사용자 시간대·실제 서버의 교체 시각을
조회하거나 시·분 단위로 실행 가능성을 보장하는 기능은 아니다. 개최 여부는 실제 지역 일정을 확인한다.

## 검색 기준: 최소코스트·최단거리·탐욕·파레토

코스트는 경로를 비교하는 **사이트의 가상 점수**다. 통조림·현금 가격도, 뽑기 수 자체도 아니다.
기본은 일반 뽑기 1회 0.02점, 확정 묶음 1회 1점, 플래티넘 티켓 1회 1점, 레전드 티켓 1회 2점이다.
화면 도움말은 일반 뽑기를 “레어티켓 1회”로 표기한다. 이 단가는 실제 사용한 통조림/티켓 금액을
자동 추적·환산한다는 뜻이 아니다. 예를 들어 일반 24회 + 확정 11연 1묶음은 기본 코스트
`24 × 0.02 + 1 × 1 = 1.48점`, 실제 뽑기 수는 `24 + 11 = 35회`다.

| 검색 기준 | 무엇을 우선하나 |
| --- | --- |
| 최소코스트 (`cost`) | 목표를 모두 얻는 후보 중 기본 가중치 합이 가장 작은 경로. 동점이면 더 앞선 도착 위치를 고른다. |
| 최소코스트(40) (`cost40`) | 같은 비교에서 일반 뽑기 단가만 0.027점으로 바꾼다. 40회 제한이나 성공률 40%라는 뜻이 아니다. |
| 최소코스트(50) (`cost50`) | 일반 뽑기 단가만 0.033점으로 바꾼다. 50회 제한이나 성공률 50%라는 뜻이 아니다. |
| 최단거리 (`distance`) | 목표를 모두 얻은 뒤 도착 위치가 앞선 경로. 동점이면 코스트를 비교한다. 일반/확정의 총 뽑기 수나 실제 지출 최소와 같은 조건이라고 단정하지 않는다. |
| 탐욕 (`balance`) | 기본 코스트에서 획득 울슈레·레레마다 각각 0.14점을 차감해 고등급 획득을 우대한다. 비교 점수는 0 아래로 내려가지 않아 0점 이후 추가 획득이 점수를 계속 낮추지는 않는다. |
| 파레토 (`pareto`) | 먼저 목표 최소코스트를 찾고, 추가 허용 `max(0.2점, 최소코스트 × 15%)` 안에서 **목표 외** 울슈레·레레 수확을 우선한다. 동률은 실제 코스트, 도착 위치 순이다. 전체 울슈레 무제한 최대화나 서로 다른 종류 수 최대화와 다르다. |

확뽑/플래티넘/레전드 **최대**는 각각 넘을 수 없는 사용 한도다. S/G의 확정 묶음 길이,
목표별 특수 티켓 허용, 해당 특수 티켓 풀 선택은 별도 조건이다. 한도만 올려 실제 확정 개최나
목표별 티켓 허용을 켠 것으로 취급하지 않는다. 결과가 `partial`/`limit`이면 현재까지의 후보일 수 있으므로
기준 이름만 보고 최적성이 검증됐다고 말하지 않는다. 조작 위치와 플랜·필터·공유는 `website` 안내를 읽는다.

## 결과 상세 조회와 페이지 커서

공유 메시지의 배열·이름/희귀도 사전·Find 경로·플랜을 먼저 읽는다. 기존 배열에 대한
후속 질문이면 시드·배너·허용 예산을 유지하고 새 배너를 검색하지 않는다. 이미 전달된
내용을 조회 도구로 다시 읽을 필요는 없다. 결과 ID가 있으면 생략된 상세를
`catsroll_result(view="summary")` 등으로 보충할 수 있다.
실행 순서는 `view="route"`, 배열 특정 구간은 `view="array"`, 캐릭터 위치는 `view="character"`,
플랜은 `view="plan"`을 사용하고 조회 응답의 nextOffset/다음 구간을 따라 필요한 페이지를 읽는다.
모델용 Find 요약의 `engine_position.next_track_offset`은 엔진의 진행 위치로, 페이지 커서가 아니다.
배열의 `nextConditionalQuery`는 행 범위를 고정한 조건부 분기 전용 계속 조회이므로 그대로 사용한다.
해당 페이지는 기본 배열 행을 반복하지 않는다. `nextStart`로 다음 행 범위로 넘어간다.
경로의 `nextOffset`이 null이면 페이지 조회를 끝낸다. `nextTrackOffset`은 엔진 진행 위치이며 페이지 커서가 아니다.
만료·미공유 결과를 prepared에서 복원하지 말고 앱에서 다시 공유하도록 안내한다.
서버가 재계산한 값이 아니라 사용자가 기기에서 계산해 공유한 스냅샷이라고 설명한다.

## 결과 필드·총 뽑기 수·생략 범위

공유된 결과에서 시작 위치, 사용할 배너, 일반/확정/티켓 행동, 획득 목표, 다음 위치를 순서대로 짧게 설명한다.
공유 결과의 `totalDraws`는 단뽑·특수 티켓·확정 묶음의 실제 뽑기 수를 합한 값이다.
행동 개수, 배열의 다음 좌표, 비용을 총 뽑기 수로 읽지 않는다. 목표 획득 회차는 공유된
획득 기록을 사용하며 확정 묶음 내부 순서가 확인되지 않으면 범위로 설명한다.
`uberDraws`는 경로에서 얻는 울슈레 수이며, 입력의 미래 울슈레 수 `ubers`와 구별한다.
배열은 압축된 행과 캐릭터 이름 사전을 함께 읽는다. 생략 수가 0이면 첫 5행뿐이라고 해석하지 않는다.
`conditionalOmitted`는 공유/조회 응답에 포함하지 않은 조건부 분기 수다. 그 분기를 실제 선택한 경로라고
추정하지 않는다. 표시 범위 끝의 `next=null`은 이 캡처에서 다음 위치가 미제공된 것이며 게임의 배열이
끝나거나 이후 뽑기가 불가능하다는 뜻이 아니다. 조건부 응답에 다른 next가 있으면 맥락을 함께 읽는다.
비용 모드는 사이트가 정한 가중치로 비교한다. 게임의 실제 현금·통조림 비용을 계산한 값으로 바꾸어 말하지 않는다.
“가장 싸게”와 “가장 적은 이동”은 다를 수 있다. 사용자가 원할 때 기준을 좁힌다.

## 기존 배열에서 울슈레 수확 비교

“울슈레 많이 먹으려면?”은 현재 배열의 희귀도 4 위치와 확정 결과를 읽어 후보를 비교한다.
중복 포함 획득 수와 서로 다른 종류 수, 뽑기 수를 함께 제시한다. 기존 목표를 유지하는
비교인지 드러내고, 목적이 달라지는 경우에만 필요한 기준을 묻는다. 기존 확뽑·티켓 예산을
임의로 늘리지 않는다. A/B에서 좋은 칸만 이어 붙이지 말고 R/G/RG·다음 좌표·조건부
선행 결과를 따라야 한다. 자료가 충분하면 AI가 후보 경로를 비교해 제안할 수 있으며,
이것을 엔진 계산이나 전체 경우의 수를 확인한 최적 경로라고 부르지 않는다.

`harvestDraws`는 목표에 포함되지 않은 울슈레·레레의 수확 지표다. cost 모드의 요약은
이 지표를 누적하지 않을 수 있어 액션 합계와 다르다. 전체 울슈레 수는 `uberDraws`,
레레 수는 `legendDraws`를 읽는다. balance는 비용에서 획득 가중치를 차감하고 pareto는
목표 최소 비용에 허용된 추가 예산 안의 수확을 비교하므로 무제한 울슈레 최대화와 다르다.

## 배너 올컬 목표 자동 선택

울슈레 올컬 목표는 `targetSelection`으로 실제 배너 풀에서 구성한다. “다마군 울슈레 전부/올컬”은 기존 배너 event/lang과 입력·예산을 보존해
`catsroll_prepare(targetSelection={type:"banner_collection",lang:기존지역,event:기존배너,rarity:4,excludeOwnedIds:명시한보유ID})`를 호출한다.
명시적 targets는 동시에 전달하지 않는다. 서버가 전체 목표를 실제 풀에서 구성하므로 모델이
명단 페이지를 합치거나 사용자에게 명단을 요구할 필요가 없다. 선택 정보에는 포함·제외 ID와
이유/개수가 있다. 울슈레 올컬은 레레를 포함하지 않는다고 밝히고 배너 전체 수집이면 범위를 확인한다.
`needs_input`이면 prepared나 계산 성공으로 설명하지 않는다. 30개 초과는 목표를 좁히도록,
남은 목표가 없으면 이미 보유한 범위임을 안내한다. 범위 내 전부 획득이 불가능할 수 있으며,
사용자가 앱에서 실행하고 공유한 뒤에만 획득·경로를 확정한다.

## 자주 묻는 질문: 재화가 이만큼인데 올컬할까요?

“통조림 5천·플티 2장으로 계획”, “콜라보 확뽑 6번이면 손해?”, “올컬했는데 더 뽑을까요?”는
획득 수·신규 종류·중복·소모와 다른 목표의 기회비용을 비교하는 질문이다. 보유 캐릭터와
원하는 범위(울슈레만/레레 포함), 현재 시드·배너·쓸 수 있는 자원을 확인한다.
`targetSelection`은 실제 풀에서 미보유 목표를 구성한다. 입력 예시는 ‘배너 올컬 목표 자동 선택’ 절을 참고한다. 이미 올컬이면 추가 뽑기는 신규 수집이
아니라 중복/다른 목적이며, 무조건 더 돌릴 이유가 있다고 말하지 않는다.

통조림 예산을 확뽑 횟수로 바꿀 때에는 게임 화면의 실제 할인·구매 단계·가격을 확인한다.
일반 뽑기를 레티/통조림 중 무엇으로 지불할지도 구분한다. 엔진 코스트를 통조림으로 환산하거나
통조림 3천이면 항상 같은 횟수라는 가정을 하지 않는다. 현재 Find의 사용 한도와 실제 지출 예산은
같은 기능이 아니므로 경로의 일반/확정/티켓 사용량을 확인한 뒤 별도로 대조한다.

일반 배너에 목표가 없거나 한도로 못 얻는 경우 선택 범위·기간을 설명한다. 더 큰 예산을 자동으로
설정하거나, 시계 변경으로 끝난 과거 배너를 쓸 수 있다는 경로를 실행안으로 내놓지 않는다.

## 결과의 한계

- `success`: 입력한 조건 안에서 찾은 경로다.
- `impossible`: 설정한 배너·범위·자원으로 경로를 못 찾았다는 뜻이다. 영원히 획득 불가라는 뜻은 아니다.
- `limit` / `partial`: 탐색 한도. 최적성이 확인된 완성 답처럼 설명하지 않는다.
- `cancelled` / 중단: 실행을 마친 결과가 아니다.

관련 문서: `tracks`, `guaranteed`, `banners`.
