# `/multi` Find 최적 경로 탐색 계획

- 상태: **설계 문서만 작성, 구현 보류**
- 작성일: 2026-08-23
- 구현 시작 조건: 현재 이벤트 필터 및 `/multi` 개선 작업을 배포한 뒤,
  깨끗한 기준 커밋에서 새 작업으로 시작한다.
- 현재 문서의 체크박스는 구현 완료 상태가 아니라 향후 작업 순서를 뜻한다.

## 1. 목표

`/multi`에서 여러 이벤트와 목표 캐릭터를 선택하면 1A부터 시작해 제한된
`count` 안에서 목표를 얻는 최적 경로를 계산한다.

경로는 다음 행동을 함께 고려한다.

- 일반 단뽑(레어티켓 또는 단뽑과 같은 1회 진행)
- 중복 레어에 의한 R 열변경
- 통조림 11연 확정뽑기에 의한 G 진행 및 열변경
- 플레티넘/레전드 티켓으로 중복 레어 열변경을 방어하는 행동
- 플레티넘/레전드 티켓에서 목표 캐릭터를 직접 얻는 행동
- 선택한 이벤트 사이의 배너 변경

배열 표시는 지금처럼 브라우저에서 먼저 끝내고, Find 탐색은 별도의
백그라운드 작업으로 뒤이어 수행한다.

## 2. 이번 작업에서 하지 않는 것

- 현재 작업 트리에는 Find 구현 코드를 추가하지 않는다.
- 현재 배포 대기 중인 이벤트 필터와 `/multi` 변경을 함께 리팩터링하지 않는다.
- 기존 Ruby `Gacha` 규칙을 Find 편의를 위해 변경하지 않는다.
- 근사 경로를 정확한 최적 경로 또는 `불가능`으로 표시하지 않는다.
- KR과 JP 이벤트를 하나의 실제 뽑기 경로로 섞지 않는다.

## 3. 용어

문서와 UI에서 `티켓`이라는 표현이 혼동되지 않도록 아래처럼 구분한다.

- **일반 단뽑**: 레어티켓 또는 동일하게 한 칸 진행하는 단뽑. 별도 가중치가
  없고 최종 도달 위치에 자연스럽게 반영된다.
- **특수 티켓**: 플레티넘 또는 레전드 티켓. 사용 1회당 비용 `+2`다.
- **확뽑**: 통조림 11연 확정뽑기. 사용 1회당 비용 `+1`이며 사용 가능
  최대 횟수를 사용자가 지정한다.
- **필수 목표**: 경로가 성공하려면 반드시 획득해야 하는 캐릭터다.
- **선호 목표**: 획득하지 않아도 경로는 성공하지만, 비용이 완전히 같은
  경로끼리 비교할 때 더 많이 얻는 경로를 우선할 수 있는 캐릭터다.
- **이벤트 목표**: 선택한 일반/확정 이벤트에서 얻어야 하는 캐릭터다.
- **티켓 목표**: 특수 티켓 배너에서 얻는 것으로 판정할 캐릭터다.

## 4. Find UI 계약

### 4.1 Find 입력 상자

Seed 검색 상자 아래, 이벤트 멀티트랙 선택 상자 위에 별도 패널을 둔다.

왼쪽부터 다음 순서로 배치한다.

1. `Use ticket` 체크박스(기본 선택)
2. 통조림 확뽑 최대 횟수 숫자 선택
3. 캐릭터 필터 버튼
4. 선택한 캐릭터를 `a, b, c` 형태로 보여주는 읽기 전용 영역

Find 설정을 변경하면 기존 상단 Apply 버튼이 다시 활성화된다. Apply를 누르면
기존 Track A/B 배열을 즉시 다시 그리고 그 후 Find 계산을 시작한다. Find 전용
Apply 버튼은 첫 구현에 추가하지 않는다.

### 4.2 캐릭터 선택 모달

이벤트 필터 모달과 동일한 기본 구조를 사용한다.

- 상단: 캐릭터명 검색
- 중앙: 선택된 캐릭터
- 하단: 선택 가능한 캐릭터 태그
- 표시 희귀도: 슈퍼레어, 울트라 슈퍼레어, 레전드 레어
- 현재 선택한 이벤트 풀에 존재하는 캐릭터를 앞에 정렬
- 그 밖의 대상 캐릭터도 검색 및 선택 가능
- 닫기, 바깥 영역 클릭 모두 현재 선택을 유지한 채 모달을 닫음

선택된 캐릭터 한 개는 내부적으로 다음 두 축을 별도로 가진다.

```text
TargetSpec {
  cat_id,
  required,       // 필수 획득 여부
  source_policy   // event 또는 ticket
}
```

권장 표시 형태:

```text
[✓ 필수] [이벤트 ▼] 아쿠아슈터 사키  ×
[  필수] [티켓  ▼] 명계의 칼리파    ×
```

- 왼쪽 `필수` 체크 시 해당 캐릭터를 얻지 못한 경로는 성공으로 인정하지 않는다.
- 기본값은 기존 Find 계약을 보존하기 위해 `필수=true`로 한다.
- `이벤트`로 지정하면 특수 티켓에서 같은 캐릭터가 나와도 목표 달성으로
  세지 않는다.
- `티켓`으로 지정하면 특수 티켓 결과에서 획득한 경우에 목표 달성으로 센다.
- 첫 구현에서는 출처를 정확히 두 종류로 유지한다. `둘 중 아무거나`는 실제
  사용 요구가 확인된 뒤 세 번째 값으로 추가한다.
- `Use ticket`을 끈 상태에서 필수 티켓 목표가 있으면 계산 전에 충돌을
  안내하고 즉시 `불가능`으로 판정한다.

필수가 해제된 선호 목표는 최종 위치와 가중 비용이 모두 같은 경로에서만
동률 결정에 사용한다. 선호 목표 때문에 더 멀리 가거나 특수 자원을 더 쓰지는
않는다.

### 4.3 브라우저 저장

Find 상태는 기존 멀티트랙 상태와 분리된 `localStorage` 키에 저장한다.

- `use_ticket`
- `max_guaranteed`
- `targets: [{cat_id, required, source_policy}]`

캐릭터 이름은 저장하지 않고 ID만 저장한다. 이름 변경이나 KR/JP 카탈로그 갱신
후에도 현재 데이터를 다시 표시할 수 있어야 한다.

## 5. 최적 경로 정의

필수 목표를 모두 획득한 경로만 후보가 된다. 후보 경로는 다음 값을 순서대로
비교한다.

```text
1. 최종 도달 위치
2. 가중 특수 행동 비용 = (특수 티켓 사용 횟수 × 2) + 확뽑 횟수
3. 획득한 선호 목표 수(많을수록 우선)
4. 안정적인 내부 탐색 순서
```

예시:

- 40B에서 끝나며 티켓 2회인 경로는 비용 `4`다.
- 40B에서 끝나며 티켓 1회와 확뽑 1회인 경로는 비용 `3`이다.
- 40B에서 끝나며 확뽑 3회인 경로도 비용 `3`이다.
- 위 두 비용 `3` 경로가 선호 목표 수도 같으면 어느 쪽도 허용되지만,
  테스트 재현성을 위해 항상 같은 내부 순서의 경로를 반환한다.
- 비용이 0이어도 41A에서 끝나는 경로는 40B에서 끝나는 비용 4 경로보다
  뒤다. 최종 목적지가 항상 가장 먼저 비교된다.

R 열변경과 일반 이벤트 전환에는 별도 비용을 붙이지 않는다. 일반 단뽑 횟수도
별도 비용으로 세지 않으며 최종 도달 위치에 포함된다.

## 6. 행동 및 목표 획득 규칙

### 6.1 일반 이벤트 단뽑

- 현재 RNG 상태와 직전 획득 캐릭터를 사용해 선택 이벤트에서 한 번 뽑는다.
- 중복 레어면 기존 게임 규칙대로 R 재추첨과 열변경을 적용한다.
- `source_policy=event`인 목표만 달성 처리할 수 있다.
- 이벤트를 바꾸더라도 직전 캐릭터 상태는 유지한다.

### 6.2 통조림 확뽑

- 실제 `guaranteed_rolls == 11`인 선택 이벤트에서만 사용할 수 있다.
- 입력한 최대 사용 횟수를 넘지 않는다.
- 10개의 일반 결과와 마지막 확정 결과 전체에서 이벤트 목표를 획득 처리한다.
- 중간 중복 레어 및 마지막 G 반 칸 진행을 기존 Gacha 규칙과 동일하게 적용한다.
- 행동 1회가 완전히 끝난 다음 위치를 경로의 도달 위치로 사용한다.
- 가중 비용은 1회당 `+1`이다.

### 6.3 특수 티켓

- `Use ticket`이 켜진 경우에만 행동 후보가 된다.
- 플레티넘/레전드 배너의 해당 RNG 위치 결과를 사용한다.
- 일반 뽑기 한 번과 같은 두 RNG 값을 소비하지만 결과가 레어가 아니므로
  중복 레어 R 전환을 방어할 수 있다.
- 중복 레어 방어가 필요한 위치뿐 아니라, 그 위치의 특수 티켓 결과가
  `source_policy=ticket` 목표인 경우에도 분기 후보가 된다.
- 특수 티켓으로 획득한 캐릭터는 이벤트 목표 달성으로 세지 않는다.
- 방어용이든 목표 획득용이든 사용 1회당 가중 비용은 동일하게 `+2`다.

### 6.4 지역 제한

- 한 번의 Find 계산에 참여하는 이벤트는 모두 같은 지역이어야 한다.
- KR과 JP 행이 함께 선택되어 있으면 계산 시작 전에 지역 선택 오류를 표시한다.
- 캐릭터 이름은 KR 데이터가 있으면 한국어명을 사용하고, 아직 KR에 없는 JP
  캐릭터만 JP 이름으로 대체 표시한다.

## 7. 필요한 데이터 계약

기존 `/track.json`은 이벤트 풀 데이터만 제공하고 실제 다중 이벤트 경로는
브라우저에서 계산한다. Find에 다음 데이터가 추가로 필요하다.

- 전체 KR/JP 캐릭터 중 희귀도 3, 4, 5의 간단한 카탈로그
  - ID
  - 한국어 우선 표시명
  - 희귀도
- 선택 이벤트별 기존 풀 데이터
- 지역별 특수 티켓 풀 데이터
  - 플레티넘 또는 레전드 구분
  - 이벤트/풀 식별자와 적용 기간
  - 희귀도 슬롯과 캐릭터 정보

카탈로그에는 설명과 이미지를 넣지 않는다. 이름, ID, 희귀도만 내려 payload와
상류 충돌 가능성을 줄인다.

특수 티켓 결과로 목표를 획득할 수 있으므로, 단순히 `레어가 아닌 임시 캐릭터`
로 처리해서는 안 된다. 정확한 티켓 풀과 해당 RNG 결과가 필요하다.

## 8. 탐색 모델

이벤트별 표의 `.next` 링크만 조합해서는 안 된다. 배너를 바꿔도 직전 캐릭터가
유지되어 숨은 R 전환 여부가 달라지기 때문이다. Find는 다음 전역 상태를 직접
추적한다.

```text
State {
  rng_seed,
  track_position,
  last_rare_or_non_rare,
  acquired_required_mask,
  acquired_preferred_mask,
  guaranteed_used
}
```

특수 티켓 횟수는 상태 지배 비교를 위한 비용 라벨에 둔다. 같은 핵심 상태에
도달했다면 가중 비용이 더 큰 경로를 버린다.

탐색은 최종 위치와 가중 비용을 순서대로 처리하는 다익스트라 또는 동등한
label-setting DP로 구현한다.

성능을 위해 다음을 적용한다.

- 목표 캐릭터 등장 위치를 이벤트별로 미리 색인
- 일반 전이를 `(seed, last rare, event)` 단위로 메모이즈
- 비레어 직전 캐릭터는 중복 레어 판정 관점에서 하나의 상태로 압축
- 같은 위치에서 결과와 다음 상태가 같은 이벤트 전이는 하나로 병합
- 특수 티켓 분기는 R 방어 지점 또는 티켓 목표 획득 지점에서만 생성
- 확뽑 분기는 실제 확정 이벤트와 남은 허용 횟수가 있을 때만 생성
- 같은 상태·획득 마스크에서는 더 큰 가중 비용 경로 제거
- `count` 밖으로 나가는 행동은 생성하지 않음

목표가 많을수록 획득 마스크가 `2^N`으로 증가한다. 구현 후 실제 벤치마크를
바탕으로 경고 기준과 상태 수 안전 한도를 정한다. 안전 한도로 중단된 경우
`불가능`이 아니라 `계산 범위 초과`로 표시한다.

## 9. 비동기 실행과 결과 표시

- 기존 Track A/B 배열을 먼저 렌더링한다.
- Find 계산은 Web Worker에서 시작한다.
- 결과 영역은 Found cats와 Track A 사이에 둔다.
- 계산 중에는 `계산 중… 5s`처럼 1초마다 시간을 갱신한다.
- Seed, count, 이벤트, 목표 또는 Find 옵션이 바뀌면 이전 Worker를 종료한다.
- 완전 탐색으로 경로가 없음을 증명한 경우에만 `불가능`을 표시한다.

결과는 일반 단뽑을 한 줄씩 모두 표시하지 않고 중요한 행동을 압축한다.

```text
8A · 이벤트 1075 · 아쿠아슈터 사키 획득 [필수/이벤트]
17A · 플레티넘 티켓 사용 · R 전환 방어 (+2)
24A~34B · 이벤트 1021 확뽑 · 명계의 칼리파 획득 (+1)
41B · 플레티넘 티켓 · 바람의 신・윈디 획득 [선호/티켓] (+2)

완료: 41B
특수 티켓 2회 × 2 + 확뽑 1회 = 가중 비용 5
필수 목표 2/2, 선호 목표 1/1
```

## 10. 충돌을 줄이는 파일 구조

새 기능의 대부분은 새 파일에 격리한다.

새 파일 후보:

- `lib/battle-cats-rolls/asset/multi-find.js`
  - Find UI, 모달, 저장, Worker 제어, 결과 표시
- `lib/battle-cats-rolls/asset/multi-find-engine.js`
  - 순수 상태 전이, 비용 비교, 탐색
- `lib/battle-cats-rolls/asset/multi-find-worker.js`
  - 백그라운드 실행, 시간/진행 메시지, 취소 경계
- `lib/battle-cats-rolls/asset/multi-find.css`
  - Find 전용 스타일

기존 파일은 다음 정도만 작게 수정한다.

  - Find 마크업, 모달, 결과 컨테이너, 새 asset 로드

## 11. 구현 단계

### Phase 0: 깨끗한 기준점 확보

목표:

- 현재 이벤트 필터와 `/multi` 개선 작업을 별도로 검증·배포한다.
- 배포 커밋과 원격 브랜치가 일치한 뒤 Find 전용 브랜치/작업을 시작한다.

완료 조건:

- 현재 작업 트리에 Find와 무관한 미완료 변경이 없다.
- 기존 전체 테스트가 통과한다.
- `/multi` 현재 동작을 브라우저에서 확인한 기준 스크린샷 또는 체크 기록이 있다.

- [ ] 지역별 어떤 플레티넘/레전드 풀을 사용할지 확정
- [ ] 모달 선택 상태와 localStorage schema 확정
- [ ] 서버 JSON 계약 테스트부터 작성

완료 조건:

- 같은 입력이 어떤 목표를 어떤 출처에서 만족시키는지 모호하지 않다.
- 티켓 풀이 바뀌는 시점과 표시 방법이 문서 및 테스트에 고정된다.

### Phase 2: Find UI만 구현

완료 조건:

## 12. 기준 예시

초기 수용 fixture:

```text
seed: 3671843074
count: 500
max guaranteed: 2
events:
  - 2026-08-21_1075
  - 2026-08-24_1021
  - 2026-08-26_1043
targets:
  - 아쿠아슈터 사키
  - 명계의 칼리파
  - 바람의 신・윈디
```

현재 데이터에서 확인된 사항:

- `2026-08-21_1075`에 아쿠아슈터 사키가 있다.
- `2026-08-24_1021`에 명계의 칼리파와 바람의 신・윈디가 있다.
- 세 이벤트 모두 11연 확정 이벤트다.

이 문서에서는 예상 최적 경로를 임의로 적지 않는다. Phase 3에서 전이 결과를
Ruby Gacha와 대조한 뒤, Phase 4에서 얻은 경로를 수동 표 추적과 다시 비교하여
golden fixture로 고정한다.

## 13. 구현 전 반드시 확정할 사항

다음 항목은 요구사항의 의미를 잘못 고정하지 않기 위해 의도적으로 미결로 둔다.

1. `티켓으로 뽑을 캐릭터`가 **티켓에서만 획득해야 하는 목표**인지,
   아니면 **이벤트 또는 티켓 중 어느 쪽으로 얻어도 되는 목표**인지 확인한다.
   현재 권장안은 출처를 정확히 구분하는 `event | ticket` 두 값이다.
2. `필수`를 해제한 목표는 현재 권장안처럼 비용이 완전히 같은 경로의 동률
   결정에만 사용할지 확인한다.
3. KR/JP에서 사용할 특수 티켓 풀을 최신 활성 풀로 자동 결정할지, 사용자가
   별도로 선택하게 할지 확인한다. 정확한 티켓 목표 계산에는 풀 버전이 반드시
   고정되어야 한다.
4. `Use ticket`은 특수 티켓 사용 전체를 허용/금지하는 전역 옵션으로 유지할지,
   보유 티켓 최대 수 입력을 추후 추가할지 확인한다. 현재 비용 모델에는 횟수
   상한이 없고 사용 횟수마다 `+2`를 적용한다.

이 네 항목을 확정하기 전에는 탐색 엔진 구현을 시작하지 않는다.
